# 기능·재미·시각·성능 검증

G001의 BASIC-12 기술 검증을 완료했습니다. 아래 장면 중 BASIC-12만 현재 코드에 있으며 다른 장면과 성능 수치는 **향후 검증 계획**입니다. 완료된 결과는 [현재 상태](../production/status.md)와 해당 PR에만 기록합니다.

## 1. 검증을 나누는 기준

| 층 | 확인하는 것 | 적합한 방식 |
| --- | --- | --- |
| 구조 | 문서·데이터·명령이 실제 존재하는가 | 현재 문서 검사, 이후 타입·lint·build |
| 게임 규칙 | 돈·좌석·주문·시간이 맞는가 | Vitest 등으로 결정적 규칙·시나리오 검사 |
| 통합 | 실제 입력에서 화면·상태·저장이 연결되는가 | 브라우저 핵심 동선과 새로고침 |
| 시각 | 현실감·가독성·자세·배치가 맞는가 | 고정 구도와 실제 이동의 전후 화면 |
| 재미 | 행동·선택·성장·애착이 생기는가 | 사람의 짧은 플레이 관찰 |
| 성능 | 밀집한 영업에서도 조작 가능한가 | 실제 GPU의 반복 장면·프로파일 |

자동 테스트를 모두 통과해도 재미와 현실적인 그래픽을 자동 통과로 표시하지 않습니다. 반대로 UI 문구 하나를 바꿀 때 전체 장기 성능 시험을 반복하지 않습니다.

## 2. 우선 보호할 규칙

| 위험 | 최소 사례 |
| --- | --- |
| 좌석 중복 점유 | 두 고객/그룹이 같은 tick에 같은 좌석 요청, 한 번만 성공 |
| 예약 유실 | 고객 이탈·경로 실패 후 예약 해제 |
| 매출 중복 | 이용 종료 재입력, 선불 충전과 사용, 중복 서빙 |
| 재고 오류 | 마지막 재료에 동시 주문, 음수 불가, 취소 시 정책대로 반환 |
| 직원과 사장 충돌 | 같은 주문 claim, 해고·실패 후 업무 반환 |
| 시간 오류 | 1·2·4배속에서 같은 sim tick과 명령 시퀀스의 결과 일치 |
| 저장 손상 | 이용·조리·서빙 도중 저장, 복원 후 중복/손실 없음 |
| 데이터 변경 | 사라진 제품·모르는 저장 버전·마이그레이션 실패 처리 |
| 배치 오류 | 점유석 이동 차단, 통로 단절 차단, 경로 재계산 |
| 화면 의존 | 카메라 밖 고객이나 낮은 품질에서도 동일한 사업 결과 |

버그는 가능하면 실패하는 재현 검사를 먼저 확인한 뒤 고칩니다. 랜덤 seed뿐 아니라 난수 상태·콘텐츠 버전·명령 적용 tick도 남깁니다. 모든 내부 함수를 테스트하기보다 실제 손실을 막는 규칙을 우선합니다.

## 3. 브라우저 검증 시나리오

| ID | 구성과 행동 | 완료 기준 |

| FIRST-SALE | 고객 입장→착석→이용→퇴장 | 좌석·현금·상태가 같은 사실을 표시 |

| GROUP-3 | 떨어진 3석과 붙은 3석 비교 | 실제 연속 좌석 규칙대로 대기·이탈·배정 |

| PEAK-60 | 60석·60 고객+직원, 주문 집중, 4배속 | 실제 상태·프레임·입력·메모리 기록 |

시나리오는 해당 기능이 구현되는 작업에서 추가합니다. 초기에 존재하지 않는 PEAK-60을 통과 처리하지 않습니다. 첫 코드 단계부터 12/24/60 배치 밀도를 불러올 수 있는 개발 장면을 점진적으로 준비합니다.

DOM 관리 UI는 role/label 같은 안정적인 요소로 조작합니다. 3D 상호작용은 고정된 카메라·장면에서 실제 클릭/이동을 한 번 이상 수행합니다. 테스트용 내부 명령만 호출하고 플레이어가 같은 일을 할 수 있다고 주장하지 않습니다.

## 4. 첫 재미 확인

G004에서 3–5명의 초기 플레이어를 시작 목표로 삼습니다. PC방에 익숙한 사람과 경영 게임에 익숙한 사람을 섞으면 유용합니다. 작은 표본의 탐색적 관찰이며 재미를 통계적으로 입증하는 시험은 아닙니다. 사람을 확보하지 못하면 미검증으로 남깁니다.

첫 20분에 말로 설명하지 않고 관찰합니다. ① 첫 손님 ② 첫 판매 ③ 작은 문제 발견 ④ 두 개선안 비교 ⑤ 변화 확인이 이어지는지 봅니다. 튜토리얼이 답을 지시해서 선택한 것인지 플레이어가 이유를 이해한 것인지 구별합니다.

| 기록 | 다음 판단 |
| --- | --- |
| 첫 행동에서 멈춘 시점과 이유 | 입력·안내·시각 단서를 고칠지 |
| 투자한 이유와 다른 선택을 버린 이유 | 실제 의사결정이 성립하는지 |
| 변화가 일어났음을 알아챈 순간 | 결과 피드백을 강화할지 |
| 기다림·반복 클릭이 지루해진 순간 | 시간 압축·작업 길이·자동화 시점을 바꿀지 |
| 다음에 스스로 개선하고 싶은 것 | 성장 동기가 생겼는지 |
| 기억에 남은 손님·매장 공간 | 애착이 단순 숫자 증가를 넘어서는지 |

G007에서는 첫 직원 고용 후 다시 관찰합니다. 반복 노동이 줄고 새 운영 판단이 생기는지 봅니다. 일이 없어져 멍하게 기다리거나, 직원 고용 후에도 같은 클릭만 더 하게 되면 다음 콘텐츠 확장보다 역할 전환을 먼저 고칩니다.

단일 돈벌이 전략만 우월한지 고정된 여러 수요 조건에서 비교합니다. 모든 전략을 똑같은 수익으로 맞출 필요는 없습니다. 실패의 이유가 관찰 가능하고 회복 가능한지를 확인합니다.

## 5. 그래픽·성능 예산

| 항목 | 초기 목표 | 상태 |
| --- | --- | --- |
| 기준 데스크톱 | RTX 3060급 GPU, 1920×1080. CPU/RAM/OS/브라우저는 실측 시 고정·기록 | 미측정 |
| 기본 동작 | 일반 영업과 만석에서 60fps 지향 | 미측정 |
| 프레임 분포 | 중앙값·p95·p99·50ms 초과 프레임 수와 연속 멈춤 기록 | 측정 방법 |
| 첫 플레이 전송량 | 필수 자산 약 30MB 이하 | 제안 목표 |
| 전체 배포 자산 | 약 250MB 이하 | 제안 목표 |
| 첫 조작 가능 시간 | 첫 실기기·네트워크 측정 후 목표 설정 | 아직 숫자 미정 |
| 저사양 옵션 | 해상도·그림자·반사·장식 조절, 규칙 동일 | 미구현 |

16.67ms는 60fps의 프레임 시간 참고값입니다. 평균 FPS 하나만 보지 않습니다. GPU 프레임 시간, JS/sim 시간, GC, draw calls, 삼각형, 텍스처·힙 메모리, 해상도와 DPR을 기록합니다. 브라우저에서 제공하지 않는 GPU 메모리 값은 추정과 실측을 구분합니다.

실기기 프로파일은 워밍업 후 같은 경로를 3분 정도 반복하고 필요하면 20–30분 영업으로 메모리 증가를 확인합니다. 1배속과 4배속을 별도 기록합니다. 서로 다른 장비 결과를 같은 표의 전후 성능 향상으로 계산하지 않습니다. 소프트웨어 WebGL을 쓰는 CI는 화면·오류 확인에 쓰고 목표 GPU 성능의 증거로 쓰지 않습니다.

콜드 캐시·전송 속도·압축 여부를 기록해 첫 전송량과 조작 가능 시간을 측정합니다. 다운로드 파일 크기, 압축 후 네트워크 전송량, GPU 메모리는 다른 값입니다.

## 6. 최적화 판단 순서

1. 같은 조건으로 병목을 재현합니다.
2. CPU 병목이면 고객 판단 빈도·경로 재계산·UI 갱신·불필요 할당을 확인합니다.
3. GPU 병목이면 해상도·그림자·반사·재질·draw calls·애니메이션을 확인합니다.
4. 로딩 병목이면 첫 필수 자산과 나중 자산을 나누고 압축·디코더·공유를 확인합니다.
5. 변경 후 같은 장면에서 규칙 유지와 시각 손실을 함께 비교합니다.

실패를 숨기기 위해 손님 수, 주문 빈도, 경제 복잡성을 품질 옵션에 따라 바꾸지 않습니다. 전체 목표가 어려우면 표현 비용을 조정하고 달성 범위를 보고합니다.
