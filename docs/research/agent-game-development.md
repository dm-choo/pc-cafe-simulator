# 에이전트와 한국 PC방 게임을 만드는 방법: 조사와 적용

조사일: **2026-09-07**. 대상: 직접 AI로 개발한 엔지니어의 경험, 에이전트 개발사의 실험, 출시 경험이 있는 게임 개발자의 제작 지침. 공개된 1차 자료를 우선했습니다. 인터뷰를 새로 진행하거나 해당 게임들을 직접 플레이한 조사는 아닙니다.

## 1. 결론과 근거의 강도

이 프로젝트의 기본 구조는 **사용자 1명 + 통합 책임을 가진 주 개발 에이전트 + 필요한 작업에서만 분리하는 리뷰·아트·검증 역할**입니다. 작업의 단위는 실제 플레이에서 확인할 수 있는 변화 하나입니다. GitHub에는 요구사항, 결정, 코드, 검증 결과와 다음 작업을 연결합니다.

이 구조가 모든 팀에 가장 빠르다는 실험 결과는 없습니다. 아래 자료를 종합해, 작은 팀이 현실풍 웹 게임을 만드는 상황에 맞춰 선택한 **프로젝트 설계안**입니다. 다중 에이전트의 수나 코드 생성량을 성공 지표로 삼지 않습니다.

## 2. 우리가 채택할 여덟 가지 원칙

### 2.1 사람이 방향을 정하고 에이전트가 결과를 연결한다

사용자는 “주문이 바쁜데 재미가 없다”, “첫 업그레이드가 더 특별했으면 한다” 같은 경험의 문제를 설명합니다. 주 개발 에이전트는 이를 조작·규칙·피드백·검증으로 바꾸고 완성된 결과로 돌려줍니다. 매 구현 단계에서 사용자를 세부 코드 승인자로 만들지 않습니다.

본 프로젝트 제안: 사용자는 재미와 시각 방향을 판단하고, 에이전트는 재현 가능한 기술 검증과 통합을 책임집니다. 별도 리뷰어가 없었던 작업은 독립 검토로 표시하지 않습니다.

### 2.2 지시는 실제 행동과 결과로 쓴다

“손님 AI를 현실적으로 구현”만으로는 완료를 판별하기 어렵습니다. 대신 “3인 손님은 연결된 3석을 찾고, 없으면 대기하다 이탈하며 실제 계산된 사유가 보인다”처럼 작성합니다. 동시에 돈·좌석·주문의 변하지 않아야 할 규칙을 지정합니다.

Addy와 OpenAI의 문맥·명세 지침을 참고하되, 매번 거대한 기획서를 다시 작성하지 않습니다. 우리 작업 계약은 [한 장짜리 입력 형식](../development/task-contract.md)으로 압축했습니다.

### 2.3 새 대화에서도 다시 시작할 수 있어야 한다

주 개발 에이전트는 현재 상태, 관련 작업, 최근 변경을 확인하고 시작합니다. 종료 시 구현한 것, 실제 검증, 실패, 다음 작업을 남깁니다. 진행률 숫자보다 “고객 이용·정산은 동작, 새로고침 복원은 아직 없음”이 유용합니다.

Anthropic의 장기 작업 실험에서 얻은 방향을 우리 게임에 적용한 것입니다. 그 실험의 수백 개 기능 목록이나 특정 SDK를 그대로 설치하지 않습니다.

### 2.4 코드 검증·화면 검증·재미 검증을 구별한다

코드: 같은 좌석에 두 고객이 배정되지 않는다. 화면: 앉는 자세가 의자와 맞고 경고가 HUD에 가려지지 않는다. 재미: 투자 전후 차이를 이해하고 다음 개선을 스스로 원한다. 세 질문은 다른 증거가 필요합니다.

Willison의 실행 중심 검증을 참고해 실제 화면을 확인합니다. 플레이어가 재미를 느꼈다는 판단은 사람의 관찰 기록으로 남깁니다. 정해진 입력을 성공시킨 자동 플레이를 재미 통과로 승격하지 않습니다.

### 2.5 작은 영업과 대표 아트를 함께 만든다

우리의 첫 제작 단위는 좌석열·카운터·손님·짧은 영업입니다. 가까이 보이는 대표 좌석 한 세트에는 최종 방향의 재질·조명·자세를 넣습니다. 나머지는 같은 규격의 임시 자산으로 연결합니다. 이후 다른 좌석 세트를 같은 방식으로 만들며 소요 시간과 웹 성능을 비교합니다.

Rami의 제작 공정 검증 관점을 가져오되, 매 단계 별도 데모를 버리는 운영은 채택하지 않습니다. 불확실한 기능은 같은 저장소의 작은 실험 분기에서 확인하고, 제품에 필요한 부분만 정리해 통합합니다.

### 2.6 그래픽의 투자 단위를 정한다

한국 PC방을 인식시키는 입구·좌석 밀도·빛·카운터, 그리고 사용자가 자주 만지는 책상·모니터·트레이를 우선합니다. 멀리 있는 제품의 포트나 나사보다 NPC 자세, 바닥과 가구의 접촉, 반복되는 재질의 일관성이 먼저입니다.

이 우선순위는 본 게임에 대한 미술·제작 판단입니다. A Short Hike의 화풍을 복제하거나 GTA V 내부 기술을 확인한 결론이 아닙니다.

### 2.7 병렬 작업은 통합 비용까지 계산한다

처음에는 한 작업을 한 책임자가 끝냅니다. 계약이 안정된 뒤 고객 규칙, 좌석 GLB 제작, 저장 마이그레이션 검사처럼 파일과 결과가 분리되는 작업만 병렬 후보로 둡니다. 같은 경제 모델·스키마·잠금 파일을 여러 작업이 동시에 바꾸는 것은 직렬화합니다.

이 방식은 연구에서 보장된 최적 인원수가 아니라 프로젝트의 시작 가정입니다. 실제 추가 에이전트 실행은 사용자의 위임과 환경 기능에 따라 이루어집니다.

### 2.8 생산성은 사용 가능한 결과로 측정한다

작업별 첫 실행까지 걸린 시간, 검토·재작업 시간, 통합 후 회귀, 에셋의 두 번째 변형 제작 시간, 사람이 실제 플레이할 수 있는 기능 수를 기록합니다. 코드 줄 수·커밋 수·에이전트 수로 속도를 주장하지 않습니다. METR의 과거 수치를 현재 성능의 예언으로 쓰지도 않습니다.

## 4. 기술 선택의 근거와 적용 범위

- [Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html): 동일 형상·재질의 반복 가구에 적용. 구역별로 나눠 큰 묶음이 화면 밖 좌석까지 그리는 낭비를 줄입니다.
- [Three.js 그림자 설명](https://threejs.org/manual/en/shadows.html): 그림자용 추가 렌더링 비용을 고려합니다. 모니터마다 그림자 광원을 만들지 않고, 고정 공간과 이동 가구의 조명을 분리합니다.
- [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html): GPU 압축 텍스처 경로를 검토합니다. 로더·지원 형식·디코더 경로까지 실제 웹 빌드에서 확인합니다.
- [Vite 정적 배포](https://vite.dev/guide/static-deploy): GitHub Pages 저장소 하위 경로를 `base`에 반영하고 빌드 산출물을 게시합니다.
- [Pages 한도](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits): 배포 자산과 트래픽을 제한 내에서 관리합니다. 로컬 아트 원본과 배포물을 구별합니다.

이 자료들은 기능이나 동작 원리를 확인해 줍니다. RTX 3060급 1080p 60fps, 첫 전송량 30MB, 전체 자산 250MB는 **우리가 검증할 목표**이며 해당 문서나 GTA V가 보증하는 수치가 아닙니다.
