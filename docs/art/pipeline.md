# 현실풍 아트와 웹용 에셋 제작

목표는 실제 한국 PC방 안을 걸으며 내 매장을 소유한 느낌입니다. GTA V는 사용자가 제시한 현실감·움직임·성능의 방향입니다. 해당 게임의 기술을 분석했다거나 같은 품질을 보장한다는 뜻은 아닙니다.

## 1. 먼저 완성할 시각 경험

| 구도 | 중요한 요소 | 흔한 실패 |
| --- | --- | --- |
| 입구에서 좌석열 | 실제 크기, 통로·칸막이, 좌석 밀도, 간판·카운터 | 텅 빈 큰 방, 균일한 무광 상자 |
| 통로를 걷는 눈높이 | 의자 비율, 모니터 높이, 반사·접촉감, 고객 자세 | 발 미끄러짐, 의자 관통, 잘못된 앉은 높이 |
| 장비를 바꾸는 가까운 시점 | 제품을 구별하는 실루엣, 적절한 재질, 설치 전후 차이 | 모든 GPU·마우스가 같은 상자, 과도한 번쩍임 |
| 카운터·주방 | 생활감, 주문 표시, 트레이·음식, 따뜻한 광원 | 장식만 있고 영업 행동과 연결되지 않음 |

사진 참고는 공간·조명·재질·동선의 범주로 모읍니다. 대표 카메라 4개를 게임 장면에 저장해 전후 비교합니다. 영화 같은 색보정으로 입력·상품·손님 상태를 못 읽게 하지 않습니다.

## 2. 제작의 순서와 책임

1. 회색 블록으로 통로·카운터·앉기 위치·카메라 높이를 확인합니다.
2. 대표 좌석 세트 1개를 모델·UV·PBR 재질·충돌·착석 지점까지 완성합니다.
3. GLB를 웹 런타임에 넣고 실제 조명·카메라·고객과 함께 확인합니다.
4. 같은 세트를 반복 배치하고 draw calls·메모리·로딩 비용을 측정합니다.
5. 두 번째 제품 변형을 같은 규격으로 만들어 제작·수정 시간을 기록합니다.
6. 통과한 방식으로 좌석·카운터·주방을 확장하고 임시 자산을 교체합니다.

에이전트는 Blender 자동화 스크립트, 모델 규격, 파일 정리, 로더와 반복 배치, 수치 검증을 도울 수 있습니다. 인물의 자연스러운 비율·리깅·착석과 최종 재질 품질은 실제 화면을 보고 반복 수정해야 합니다. Blender나 에셋 도구를 실행하지 않았다면 “제작 완료”로 기록하지 않습니다.

## 3. 런타임 자산 계약

| 항목 | 시작 규격 |
| --- | --- |
| 크기·좌표 | 1단위=1m, 런타임 Y-up, 내보내기 때 좌표 변환 확인 |
| 피벗 | 가구는 배치 기준점, 의자는 좌석 기준과 정면 방향 문서화 |
| 이름 | 안정적 자산 ID와 버전. 예: `seat.standard.01`, `chair.fabric.01` |
| Mesh | 필요 없는 내부 면·숨은 부품 제거, 재질 슬롯 절약 |
| 재질 | PBR base color / roughness / metallic / normal 중심, 색 공간 일치 |
| 충돌 | 별도 저복잡도 프록시·접근 지점. 렌더 Mesh 전체를 충돌로 쓰지 않음 |
| LOD | 가까이 구별되는 실루엣 보존, 중·원거리 단순화. 전환은 실제 이동으로 확인 |
| 애니메이션 | idle / walk / sit-enter / seated / sit-exit / 작업의 최소 세트 |
| 파일 | 웹용 GLB와 필요한 압축 텍스처, 동일 디코더 버전·경로 기록 |

가구와 장비의 설치 ID는 제품 데이터와 분리합니다. 서로 다른 제품이 초기에는 하나의 표현 자산을 공유할 수 있지만 구매 UI에서는 그 제한을 오해하지 않도록 표시하고, 주요 차이는 나중에 교체 가능하게 둡니다.

## 4. 조명·화면·반사

고정 건물과 이동 가능한 가구를 분리합니다. 고정 공간의 간접광을 베이크하고 움직이는 대상에는 일관된 보조광·환경 반사와 필요한 그림자를 적용합니다. 이동 가구의 그림자를 바닥에 구워 두면 배치 후 유령 그림자가 남으므로 피합니다.

모니터는 emissive 재질과 공유 화면 자산으로 시작합니다. 화면마다 별도 동영상과 그림자 광원을 켜지 않습니다. 먼 화면은 낮은 빈도로 갱신하고 재생 자산을 공유합니다. 실제 게임 이름의 데이터와 배포 가능한 화면 자료의 권리를 따로 관리합니다.

반사는 환경맵 중심으로 시작하고 실제 플레이에서 효과가 큰 표면만 추가 검토합니다. 거리·품질 단계에 따른 장식 감소는 허용하지만 고객 수나 경제 규칙을 줄여서는 안 됩니다.

같은 형상·재질의 반복 물체는 구역별 인스턴싱 후보입니다. 인물은 리그·포즈·재질의 공유 가능성과 애니메이션 비용을 별도로 검토합니다. 모든 skinned mesh가 `InstancedMesh`로 자동 해결된다고 가정하지 않습니다. [Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html), [그림자 비용](https://threejs.org/manual/en/shadows.html)

## 5. 자산 예산: 측정 후 조정할 출발점

| 대상 | 출발 예산 | 검토 방식 |
| --- | --- | --- |
| 일반 소품 텍스처 | 주로 512–1024, 공유 우선 | 가까운 플레이에서 해상도가 실제로 필요한지 |
| 대표 제품·인물 텍스처 | 주로 1024–2048 | 작은 물체에 불필요한 4K 금지 |
| 좌석 세트 | 근거리 합계 약 15k–35k 삼각형부터 시험 | 반복 수와 shadow pass 포함 실제 비용 |
| 고객 모델 | 가까운 모델 약 15k–30k, 먼 모델 단순화 | 60명과 직원의 애니메이션·메모리 |
| 전체 프레임 | 대표 장면 draw calls 약 250 이내를 초기 진단선으로 | 엄격한 합격선이 아닌 병목 추적 신호 |

모든 예산은 제안입니다. 브라우저/GPU/재질·그림자에 따라 같은 삼각형 수의 비용도 다릅니다. 보기 좋은 대표 장면과 실측 결과를 토대로 바꿉니다. 최종 성능 목표는 [검증 문서](../quality/validation.md)에 한 번만 정의합니다.

텍스처는 KTX2/Basis 경로를 검토하되 다운로드 크기뿐 아니라 변환 시간·GPU 메모리를 확인합니다. Mesh 압축은 하나의 경로부터 시험하고 작은 모델에 디코더 비용이 더 큰지 봅니다. 필요한 디코더·WASM도 Pages base 경로 아래에서 로드되는지 확인합니다. [KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)

## 6. 원본·배포물·출처

`assets/manifest.json`은 현재 비어 있는 실제 자산 등록부입니다. 첫 자산부터 ID, 런타임 경로, 원본 위치/버전, 제작자·출처 URL, 라이선스/사용 조건, 크기, LOD, collider, export 절차를 기록합니다. 예제 자산을 실제 제작된 것처럼 등록하지 않습니다.

작은 배포 GLB·텍스처와 manifest는 Git에 넣습니다. 큰 `.blend`·원본 텍스처가 생기면 Git LFS 또는 별도 원본 저장 위치를 선택하고 접근·버전·재현 방법을 기록합니다. 현재 LFS는 설정하지 않았습니다. LFS 포인터만 배포물로 올라가지 않게 빌드 때 실파일 존재를 검사해야 합니다.

첫 완성판은 에셋 마켓 구매를 필수로 하지 않습니다. 구매가 필요한 경우 원하는 자산, 가격, 사용 조건과 기대 효과를 먼저 제시합니다. 외부 상품 화면·로고·음악의 사용 가능 여부를 자동 추정하지 않습니다. 향후 UE5 전환을 고려해 원본과 범용 자산을 보존하지만 웹 코드가 자동으로 UE5로 이전된다고 약속하지 않습니다.

## 7. 에셋 PR의 완료 조건

- 실제 게임에서 로드되고, 크기·피벗·정면·착석이 맞습니다.
- 통로와 배치 collider가 렌더 형상과 납득 가능하게 맞습니다.
- 대표 카메라와 이동 중의 시각 오류를 확인했습니다.
- 파일·메모리·draw call 변화와 출처를 기록했습니다.
- 임시 자산 교체 후 제품 ID와 저장 복원이 유지됩니다.

파일을 내보냈다는 것과 웹 게임에 통합했다는 것은 별개의 상태입니다.
