# 사람·에이전트 협업 방식

이 문서는 [조사 보고서](../research/agent-game-development.md)를 이 게임에 적용한 운영안입니다. 기본은 한 주 개발 에이전트가 한 기능을 끝까지 연결하는 방식입니다. 아래 역할은 별도 인원이나 상시 실행 프로세스가 필요한 조직도가 아닙니다.

## 1. 역할과 산출물

| 역할 | 책임 | 넘겨줄 결과 |
| --- | --- | --- |
| 사용자 / 게임 디렉터 | 원하는 플레이 경험, 현실감·그래픽 취향, 범위의 방향, 사람 플레이테스트 | 플레이하며 느낀 문제·기대·선호의 구체적인 예 |
| 주 개발 에이전트 / 통합 책임자 | 작업 분할, 관련 자료 확인, 코드·데이터·화면 연결, 검증·수정·PR 준비 | 실행 가능한 기능, 증거, 변경 이유, 남은 문제 |
| 리뷰 역할 | 요구사항·설계·실제 diff를 읽고 실패 사례 탐색 | 재현 가능한 결함, 영향, 꼭 고칠 것과 선택 개선 구분 |
| 아트 역할 | 모델·재질·애니메이션·광원·사운드의 일관성과 웹용 변환 | 런타임 자산, 원본 위치, 제작·출처 기록, 대표 장면 |
| 플레이테스트 역할 | 사람이 조작하며 재미·이해·리듬 관찰 | 막힌 시점·선택 이유·지루함·다음에 하고 싶은 것 |

초기에는 주 개발 에이전트가 구현·자기검토·브라우저 검증을 순서대로 합니다. 중요한 경제·저장 변경은 가능하면 다른 세션이나 사람의 검토를 추가합니다. 같은 에이전트의 자기검토는 유용하지만 독립 검토로 부르지 않습니다. 에셋 제작 도구나 사람이 없으면 할 수 있는 작업과 남은 수동 제작을 구별합니다.

## 2. 세 가지 도구의 책임을 구별한다

| 도구 | 하는 일 | 이 프로젝트에서의 위치 |
| --- | --- | --- |
| 이 대화의 GitHub 플러그인 | 허용된 저장소·파일·이슈·PR 작업 | 요구와 결과를 저장소에 연결하는 통로 |
| Codex 등 실행 가능한 개발 에이전트 | 코드 편집, 명령 실행, 테스트, 브라우저 관찰 | 주 개발 실행 환경 |
| GitHub Copilot cloud agent | 별도 활성화된 GitHub 실행 환경에서 작업과 PR 수행 | 사용 가능할 때 선택하는 다른 실행 경로 |

GitHub 플러그인 연결만으로 Copilot 구독·자동 개발 실행·신규 저장소 생성 권한까지 생기지 않습니다. Copilot cloud agent는 별도의 기능이며 저장소 설정과 사용 자격을 확인해야 합니다. [GitHub 공식 개요](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)

이 게임 자체에는 LLM 호출이 필요하지 않습니다. 개발 도구의 AI 사용과 손님의 게임 내 행동 로직을 분리합니다. 처음부터 Agents SDK 서버나 상시 자동 작업 봇을 구축하지 않습니다.

## 3. 한 작업의 시작부터 종료까지

1. **재개:** AGENTS, 현재 상태, 관련 이슈/작업서, Git 상태와 최근 변경을 확인합니다. 이미 승인된 작업은 다시 허락을 묻지 않습니다.
2. **현재 기준 확인:** 수정 전 관련 검사를 실행합니다. 게임이 존재하면 짧은 기본 영업 흐름도 확인합니다. 기존 실패와 이번 회귀를 구별합니다.
3. **작업 계약:** 플레이어가 할 행동, 영향을 주는 상태, 수정 범위, 완료 기준을 정합니다. 모호한 구현 선택은 합리적 가정을 기록하고 진행합니다.
4. **구현:** 한 기능을 규칙→명령/이벤트→화면→저장 영향까지 연결합니다. 작업 중 발견한 연관 오류는 필요한 범위에서 고치고 범위를 설명합니다.
5. **검증:** 경제·저장 등 중요 규칙 검사, 브라우저 조작, 필요한 장면 확인을 수행합니다. 사람의 재미 평가는 별도로 기록합니다.
6. **검토와 수정:** 요구와 diff를 대조하고 엣지 케이스를 확인합니다. 실제 문제가 없으면 선택적인 리팩터링 때문에 계속 확장하지 않습니다.
7. **인수인계:** 커밋·PR에 목적, 플레이 방법, 검증 결과, 한계, 다음 작업을 남깁니다. 현재 상태와 영향받은 기준 문서만 갱신합니다.

긴 작업은 [작업 계약](task-contract.md)의 실행 메모를 갱신하면서 진행합니다. 작업이 세션 경계를 넘었다는 이유로 처음부터 재설계하지 않습니다.

## 4. 브랜치·리뷰·통합

`main`은 현재 검증된 진행 상태입니다. 작업 브랜치 예시는 `feat/g002-seat-session`, `fix/g006-order-double-complete`, `art/g003-seat-set`입니다. 완료할 수 있는 단위로 PR을 나누되 모든 작은 파일을 개별 PR로 만들 필요는 없습니다.

PR의 기준 질문은 다음과 같습니다.

- 어떤 플레이 경험 또는 구체적 오류를 바꾸는가?
- 플레이어가 어디서 어떻게 확인하는가?
- 같은 금액이 두 번 반영되거나 저장 상태가 깨지는가?
- 시각 변화는 대표 장면에서 확인했는가?
- 아직 확인하지 않은 것은 무엇인가?

새 커밋으로 동작이 바뀌면 관련 검사와 증거를 갱신합니다. 과거 커밋의 통과 결과만으로 새 결과를 통과 처리하지 않습니다. 사람이 보기 위한 영상·스크린샷에는 커밋, 장면, 품질 설정을 함께 기록합니다.

기본 개발 흐름은 PR 검토 후 통합입니다. 병합과 배포를 사용자가 이미 승인했다면 반복 확인하지 않고 필요한 검증을 마칩니다. 승인되지 않은 공개 전환, 유료 구매, 공유 이력 강제 덮어쓰기 등은 기존 작업의 연장으로 추정하지 않습니다. 저장소 보호 규칙을 우회하지 않습니다.

## 5. 병렬화가 도움이 되는 조건

첫 영업을 연결하기 전에는 공유 설계가 많이 바뀌므로 직렬 진행합니다. 별도 작업을 위임하도록 승인받고 입출력 계약이 안정됐을 때만 병렬로 진행합니다.

| 함께 진행하기 좋은 작업 | 먼저 합쳐야 하는 작업 |
| --- | --- |
| 확정된 좌석 규격의 GLB와 고객 선호 데이터 조사 | 좌석 ID·좌표·배치 규칙 변경 |
| 고객 규칙의 독립 검토와 아트 최적화 | 돈·주문·저장 형식 변경 |
| 확정된 스냅샷을 표시하는 관리 UI와 음식 아이콘 | 공유 이벤트·명령 형식 변경 |

각 작업은 맡은 파일, 기준 커밋, 변경하지 않을 공통 계약, 산출물, 검사 명령을 적습니다. 같은 로컬 환경이면 작업별 worktree/브랜치를 사용하고, 원격 에이전트이면 해당 브랜치를 사용합니다. 잠금 파일·공통 타입·진행 상태는 통합 책임자가 충돌을 정리합니다. `.blend` 같은 바이너리 원본은 한 번에 한 담당자가 편집합니다.

계약 변경이 필요해지면 그 변경을 먼저 통합한 뒤 의존 작업을 갱신합니다. 여러 에이전트가 같은 작업을 중복 구현해 가장 큰 결과를 고르는 방식을 기본으로 삼지 않습니다.

## 6. 에이전트에게 실제로 줄 지시 예

### 기능 구현

```text
G002 고객 이용을 구현해줘. 현재 상태와 백로그의 G002를 기준으로 해줘.
고객은 사용 가능한 좌석을 하나만 점유하고, 이용 종료 후 점유를 해제해야 해.
좌석이 없을 때 현금이 늘거나 고객이 의자 위에 겹치면 안 돼.
고객 상태와 이용 매출은 sim이 소유하고 UI는 명령과 조회만 사용해줘.
관련 규칙을 검증하고 브라우저에서 입장→착석→퇴장을 확인해줘.
PR에는 실제 결과와 아직 없는 저장·음식 기능을 명시해줘.
```

### 결함 수정

```text
직원이 서빙하는 동안 내가 같은 주문에 상호작용하면 음식 매출이 두 번 잡혀.
주문 claim/완료 상태를 확인하고 재현되는 검사부터 만든 뒤 고쳐줘.
주문 UI만 비활성화해서 숨기지 말고 sim에서 중복 완료를 막아줘.
직원이 해고되거나 길이 막힐 때 주문이 영원히 잠기지 않는지도 확인해줘.
```

### 화면 개선

```text
입구에서 좌석열을 볼 때 장난감처럼 보여. 아트 제작 문서의 기준을 적용해줘.
비율·거칠기·노출·접촉 그림자와 앉은 자세를 먼저 확인해줘.
같은 카메라와 장면으로 전후 화면을 비교하고 변경의 프레임 비용을 기록해줘.
정면 한 장만 예쁘게 만드는 대신 통로를 걸으며 어색한 부분을 고쳐줘.
```

## 7. 협업 효율을 점검하는 방법

첫 세 기능이 통합되면 PR마다 작업 시간, 재작업, 검증 누락, 인수인계 재탐색 비용을 짧게 기록합니다. 병렬 작업을 도입한 뒤에는 충돌 해결 시간이 실제로 늘었는지 봅니다. 기록은 선택을 바꾸는 데 필요한 수준으로만 유지합니다.

기능보다 문서가 계속 먼저 늘거나, 에이전트의 답을 검토하는 시간이 구현 시간을 넘으면 작업을 더 명확하고 작게 나눕니다. 매번 새로운 프레임워크·에이전트 설정을 추가해서 해결하지 않습니다.
