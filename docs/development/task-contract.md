# 작업 계약과 완료 기준

작업 계약은 기능 하나를 다른 세션에서도 이어갈 수 있게 하는 입력입니다. [백로그](../production/backlog.md)의 내용을 복사해 실제 이슈로 옮기고, 프로젝트 내부 ID `G001` 등을 유지합니다. GitHub 이슈 번호는 생성 후에만 기록합니다.

## 입력 템플릿

```markdown
# G번호: 플레이어가 확인할 변화

상태: ready / in-progress / blocked / in-review / done
관련 이슈·기준 커밋: 실제 값 또는 미등록

## 목적
누가 어떤 상황에서 무엇을 할 수 있게 되는가? 왜 재미/운영에 필요한가?

## 범위
포함하는 행동과 데이터. 이번 작업에서 다루지 않는 인접 기능.

## 문맥과 소유권
관련 기준 문서·코드. 담당 파일. 먼저 필요한 작업과 안정된 공통 계약.

## 완료 조건
사용자 행동 → 기대되는 관찰 가능한 결과.
돈·좌석·주문·시간·저장 등 유지할 규칙.

## 검증
실행할 현재 명령과 브라우저 재현 방법. 필요한 사람 검증.

## 실행 메모
결정, 진행, 실패, 실제 결과, 이어받을 다음 행동.
```

## 완료의 의미

| 분류 | 필요한 증거 | 필요하지 않은 것 |
| --- | --- | --- |
| 문서/기초 구성 | 실제 파일과 링크·구조 검사 | 아직 없는 게임의 가짜 실행 결과 |
| 규칙/저장 수정 | 요구 조건과 실패 사례를 확인하는 검사 | 구현 내부를 그대로 복사한 테스트 |
| 화면/상호작용 | 브라우저 조작과 관련 장면 확인 | 화면 하나의 픽셀 차이만으로 품질 판정 |
| 성능 개선 | 같은 조건의 전후 측정, 달라진 조건 명시 | 빈 매장 평균 FPS만으로 만석 성능 주장 |
| 재미/밸런스 변화 | 사람이 고른 이유·이해한 효과·지루한 구간 | 에이전트가 재미 점수를 만들어 통과 처리 |

작은 가역적 수정에 불필요한 테스트나 문서를 추가하지 않습니다. 반대로 돈·저장 손실처럼 오류 영향이 큰 변화는 눈으로 한 번 본 것만으로 끝내지 않습니다. 사용자 승인과 기술 검증은 서로 다른 문제입니다.

## 중단 또는 재개 메모

“80% 완료” 대신 아래를 남깁니다.

```text
구현: 단체 고객의 연속 좌석 검색과 예약 해제.
확인: 동일 그룹의 중복 좌석 요청 방지 검사 통과.
미확인: 브라우저에서 3인 동시 착석 자세.
문제: 통로 변경 후 고객 경로가 이전 배치를 참고함.
다음: layout revision으로 경로 무효화 후 장면 GROUP-3을 확인.
```

재현용 seed·커밋·설정이 있으면 함께 남깁니다. 실제 실행하지 않은 출력이나 통과 수를 작성하지 않습니다.
